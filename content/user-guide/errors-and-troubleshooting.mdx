# Errors and Troubleshooting

When Mirador cannot display a resource or render tiles correctly, the problem almost always stems from network restrictions, CORS headers, invalid JSON structure, or server permission issues.

Use this guide to diagnose and resolve the most common errors.

---

## 1. CORS (Cross-Origin Resource Sharing) Errors

**Symptom**: You paste a manifest URL or image service into Mirador, but the viewer displays an error: *"Unable to load resource"* or the browser console shows:
`Access to fetch at 'https://...' from origin 'https://...' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.`

### Cause:
Browsers enforce the Same-Origin Policy. When Mirador running on `domain-a.org` requests a manifest or image tiles from `domain-b.org`, `domain-b.org` MUST include the following HTTP response header:
```http
Access-Control-Allow-Origin: *
```

### Resolution:
- **Server Administrators**: Configure the web server (Apache, Nginx, CloudFront, S3) serving manifests and image tiles to send `Access-Control-Allow-Origin: *`.
- **End Users**: If you do not control the hosting server, test the manifest using a CORS proxy or an instance of Mirador hosted on the same domain as the resource.

---

## 2. Invalid or Malformed JSON-LD Manifest

**Symptom**: The manifest fails to load, or the window opens with an empty or broken canvas view.

### Troubleshooting Steps:
1. Open the manifest URL directly in your browser or a JSON formatter.
2. Verify that the response returns HTTP status `200 OK` and valid JSON.
3. Validate the manifest using the official [IIIF Presentation Validator](https://presentation-validator.iiif.io/):
   - Check for missing `@id` (v2) or `id` (v3) properties.
   - Ensure every `Canvas` declares valid `width` and `height` dimensions.
   - Confirm that canvases declare valid painting annotations pointing to reachable IIIF Image API services or static files.

---

## 3. Mixed Content Warnings (HTTPS vs. HTTP)

**Symptom**: If your Mirador instance is served over HTTPS (secure), but the manifest URL or image tile services use insecure HTTP:
`Mixed Content: The page at 'https://...' was loaded over HTTPS, but requested an insecure resource 'http://...'. This request has been blocked.`

### Resolution:
All manifest URIs, canvas IDs, and image service URLs must use HTTPS (`https://`) when running on an HTTPS-secured website.

---

## 4. Deep-Zoom Image Tiles Failing (Grey or Blank Canvases)

**Symptom**: The manifest loads, metadata and table of contents are visible, but the main image canvas remains blank, grey, or shows broken tile icons.

### Troubleshooting Steps:
1. Open the browser's Developer Tools (`F12`) and inspect the **Network** tab.
2. Filter by `Img` or `Fetch/XHR`.
3. Check the HTTP response status for tile requests:
   - **404 Not Found**: The image server path is misconfigured in the manifest's `service` block.
   - **401 Unauthorized / 403 Forbidden**: The image server requires authentication or an active token. See [Working with Protected or Authenticated Resources](/user-guide/working-with-protected-or-authenticated-resources).
   - **500 Internal Server Error**: The remote IIIF image processor (e.g., Cantaloupe, Loris, IIPImage) is crashing or out of memory.

---

## 5. Diagnostic Checklist

Before opening an issue or contacting repository administrators, run through this checklist:

1. **Test in the Official Live Demo**: Try loading the manifest in the [Mirador Live Demo](https://projectmirador.org/demo/). If it fails there as well, the issue is with the manifest or remote server, not your local setup.
2. **Inspect the Console**: Press `Ctrl+Shift+I` (or `Cmd+Option+I` on Mac) and check the **Console** tab for red error messages.
3. **Check the Specification Matrix**: Review the [Mirador IIIF Support Matrix](/iiif-support) to verify whether the feature or API version you are attempting to use is supported.
